# 建模手工作流程

## 角色边界

建模手控制全题逻辑、模型合同和结论边界。编程手负责可靠实现、真实计算和结果证据；论文手负责把已经确认的模型与结果表达清楚。实现或写作发现问题时必须回写模型合同，不能静默改变模型。

## 1. 全题拆解

完整读取题目和附件，建立 `建模总控.md`：逐问记录结论目标、输入输出、单位、问题依赖、硬条件、歧义、风险和降级路线。先判断描述/解释/预测/评价/决策任务，再判断时间、空间、随机性、数据生成和约束结构。每个递进子问题都与上一问比较；新增离散决策、组合约束、资源配置、时序、风险或不确定性时，重新判断是否升级为决策/组合优化或“统计 + 决策优化”。第三问优先检查，但不预设为 NP-hard。

## 2. M0 建模逻辑门

按 `references/建模手总控协议.md` 编制 `模型合同.md` 与 `术语与符号表.md`。对题目事实、数据发现、领域依据、建模假设、设计选择和未知项分别标记。

候选阶段通常提出 2–4 个模型族；实现阶段按“主方案最小纵向闭环 → 廉价审计基线 sanity check → 主方案全量计算”推进，强备选只在主方案失败或需要独立稳健性验证时实现。不得把模型数量、复杂度或优秀论文出现频率当作选型证据。

建模手能够独立解释目标、假设、方程、约束、候选取舍、失败条件和结论边界后，将状态标记为 `M0 通过`；否则退回修改。

## 3. 向编程手交付

模型合同必须包含：

- 数据字段、单位、索引和只读输入；
- 变量、参数、目标函数、全部约束和边界条件；
- 每条公式和约束的现实含义与来源；
- 输入输出接口、算法建议、停止条件和求解状态要求；
- 基线、主方案、验证指标、最小测试和降级条件；
- 后问需要的中间量及不确定性表达。

## 4. 实现回审

编程手返回最小原型后，检查代码是否忠实实现模型合同，重点核对变量域、索引范围、约束方向、单位、时间顺序、随机种子和停止条件。实现需要改变假设、参数或数学结构时，先更新合同并重新确认受影响部分。

## 5. 结果回审

得到全量结果后，执行量纲、数量级、边界/特例、约束回代、基线对照、与题型匹配的样本外或稳健性验证和结论边界检查。确认求解状态是最优、近优、可行、不可行还是未收敛，不能只看输出数值。若预测只是决策模型的输入层，继续检查最终决策质量、风险、硬约束和不确定性传播，不能只用预测指标裁决整套方案。

主方案满足“完整作答、假设无明显冲突、至少一种合适验证、硬约束满足、最强备选不改变主结论、可复现、关键数值独立回代”后立即冻结并进入下一问。冻结后只对数据泄漏、目标定义错误、核心约束违反、明显计算错误、模型结构失效或可能改变主要结论的问题解冻；其余问题记入局限或附录。

## 6. 跨问与论文交接

检查前问输出到后问的名称、索引、单位、时间尺度和误差传播。每问向论文手交付一页模型逻辑、公式和约束来源、结果表、验证证据、现实解释及禁止外推项。

独立 Agent 质检可用于增加信心，但缺少 Subagent 不自动阻断比赛流程；可由未参与该部分的队员交叉复核，并如实记录复核范围。
